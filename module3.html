    UML in the SDLC

    Thinking about the Software Development Life Cycle (SDLC), it's not a rigid, linear process but rather an iterative and often overlapping set of phases. Different UML diagrams shine in different phases:
    - Requirements/Analysis: This is where what the system needs to do is thought about. Use Case diagrams are fantastic here for capturing user interactions and system responses. Class diagrams can start to emerge as you identify key concepts and their relationships. Activity diagrams can help visualise workflows and processes.
    - Design: This focuses on how the system will work. Class diagrams become more detailed, showing attributes, operations, and relationships. Sequence diagrams and Communication diagrams (which are similar but focus on object organisation) are great for illustrating interactions between objects over time. State Machine diagrams are important for modelling the behaviour of objects with distinct states and transitions. Component diagrams and Deployment diagrams also come into play to show the system's physical structure and deployment environment.
    - Implementation: While code is the primary focus here, diagrams can still be helpful for understanding complex parts of the system or for reverse engineering existing code. Class diagrams and Sequence diagrams can be useful for this.
    - Testing: Diagrams, particularly Use Case diagrams and Activity diagrams, can inform test case design by providing a visual representation of system behaviour and user interactions.
    - Maintenance: When making changes or fixing bugs, diagrams can be invaluable for understanding the system's structure and behaviour, especially if the original documentation is lacking.

    A Washing Machine State Machine


    A conceptual outline of the states and transitions:
    1- Idle: The machine is off, waiting for input.
    2- Filling: Water is filling the drum.
    3- Washing: The drum is rotating, washing the clothes.
    4- Rinsing: The drum is rotating with fresh water to rinse the clothes.
    5- Spinning: The drum spins at high speed to extract water.
    6- Draining: Water is being pumped out of the drum.
    7- Finished: The cycle is complete.
    And here are the transitions:
    - From Idle to Filling: Triggered by the "Start" button.
    - From Filling to Washing: When the water level is sufficient.
    - From Washing to Rinsing: After the wash cycle time is complete.
    - From Rinsing to Spinning: After the rinse cycle time is complete.
    - From Spinning to Draining: After the spin cycle time is complete.
    - From Draining to Finished: When the drum is empty.
    - From Finished to Idle: Automatically after a short period, or by user intervention.

    Reflection:

    Creating this model for a washing machine helps clarify the different stages a washing machine goes through. It's not just a linear sequence; there are implicit conditions (like water level) and timing considerations that drive the transitions. A state machine diagram makes these explicit.
    This kind of modelling is immensely useful during the design phase. It helps ensure that all possible states and transitions are considered, preventing potential bugs and ensuring the system behaves as expected. It also serves as a great communication tool between developers, testers, and even non-technical stakeholders.
    By using UML diagrams strategically throughout the SDLC, we can improve communication, reduce ambiguity, and ultimately build better software.

    if Statements in python:
    - Decision Making: if statements are the cornerstone of decision-making in programming. They allow code to execute different blocks of code based on whether a certain condition is true or false. This enables programs to respond dynamically to various inputs and situations.
    - Control Flow: if statements, along with their companions elif (else if) and else, provide control over the flow of execution in a program. They enable the creation branches in code, determining which parts are executed and which are skipped.
    - Error Handling: if statements are invaluable for error handling. They can be used to check for potential errors or exceptional conditions and execute specific code to handle them gracefully, preventing the program from crashing.
    - User Interaction: if statements play a crucial role in creating interactive programs. They allow code to respond to user input, making applications more user-friendly.
    Polymorphism in python:
    - Flexibility and Extensibility: Polymorphism allows objects of different classes to be treated as objects of a common type. This provides great flexibility and extensibility within code. It can be used to easily add new classes without modifying existing code that interacts with them, as long as they adhere to the common interface.
    - Code Reusability: Polymorphism promotes code reusability. You can write generic code that works with objects of different classes, reducing redundancy and making the code more concise and maintainable.
    - Abstraction: Polymorphism enables abstraction by allowing the focus to be on the common interface of objects rather than their specific implementations. This simplifies code and makes it easier to understand and reason about.
    - Dynamic Dispatch: Polymorphism is often implemented using dynamic dispatch, which means that the actual method that is executed is determined at runtime based on the object's type. This allows for greater flexibility and adaptability within code.

    Activity 1: Relevance of Cyclomatic Complexity in Object-Oriented Systems


    Cyclomatic complexity (CC), as defined by McCabe (1976), measures the number of linearly independent paths through a program's source code. While useful for procedural programming, its applicability to object-oriented (OO) systems is limited. CC focuses on control flow within individual methods, neglecting the complexities introduced by core OO principles.
    Limitations of CC in OO Contexts:
    - Inheritance and Polymorphism: These features introduce dynamic dispatch, where the actual method executed is determined at runtime. CC, being a static analysis metric, cannot fully capture the complexity arising from polymorphic behaviour (Chidamber & Kemerer, 1994). A single method call can lead to different execution paths depending on the object's type, which CC doesn't account for.
    - Object Interactions: OO systems are characterised by interactions between objects. CC focuses on intra-method complexity, disregarding the inter-object relationships and message passing that contribute significantly to overall system complexity (Li & Henry, 1993).
    Alternative Metrics for OO Complexity:
    Several metrics have been proposed to better capture the complexities of OO systems:
    - Weighted Methods per Class (WMC): This metric sums the complexity of all methods within a class. It provides a more comprehensive view of class complexity than simply considering the number of methods (Chidamber & Kemerer, 1994).
    - Depth of Inheritance Tree (DIT): This metric measures the length of the inheritance path from a class to the root of the inheritance hierarchy. Deeper inheritance hierarchies can indicate increased complexity due to potential code reuse and overriding complexities (Li & Henry, 1993).
    - Coupling Between Objects (CBO): This metric quantifies the number of classes to which a given class is coupled. High coupling can lead to increased complexity, reduced reusability, and increased maintenance effort (Chidamber & Kemerer, 1994).
    - Lack of Cohesion of Methods (LCOM): This metric measures the dissimilarity of methods within a class based on the attributes they access. High LCOM indicates low cohesion, which can suggest design flaws and increased complexity (Chidamber & Kemerer, 1994).

    Activity 2: Relevance of Cyclomatic Complexity in Object-Oriented Code:


    Thinking about cyclomatic complexity in the context of OO code is like trying to understand a complex ecosystem by only counting a single type of organism.
    In OO programming, classes are like individual organisms, and their interactions are what truly define the system's complexity. CC only looks at the "paths" within a single method, ignoring the crucial relationships between objects, the inheritance hierarchies that define their behaviour, and the dynamic dispatch that makes OO systems so powerful.
    While CC can be useful for understanding the internal complexity of a single method, it's insufficient for grasping the overall complexity of an OO design. We need to consider other metrics that capture the essence of object-oriented principles, such as coupling, cohesion, and inheritance depth, to truly understand the "ecosystem" we've created. It is like using a microscope to view a forest. You can see the details of a single leaf, but you miss the forest for the trees.

    - Adds complexity to development process
